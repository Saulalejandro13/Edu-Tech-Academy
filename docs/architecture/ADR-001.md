# ADR-001 — Uso de Domain Model como patrón principal

**Estado:** Aceptado.

## Contexto

EduTech Academy necesita gestionar reglas de negocio complejas relacionadas con certificaciones, cupos, pagos, cambios de grupo, modificaciones de calificaciones, reinscripciones y sustituciones de instructores.

Algunas reglas pueden cambiar, como la asistencia mínima, los plazos de pago y los límites de cambios de grupo. Por ello, se necesita una arquitectura que centralice estas condiciones y mantenga la consistencia del sistema.

## Decisión

Se selecciona **Domain Model** como patrón arquitectónico principal.

Las reglas de negocio se encapsulan en entidades, agregados y objetos de valor como Curso, Inscripción, RegistroAcadémico, Certificado, Cupo y Nota.

## Alternativas consideradas

- **Transaction Script:** permite implementar operaciones individuales, pero puede provocar duplicación de reglas.
- **Table Module:** organiza las operaciones por tablas, aunque resulta menos adecuado para representar comportamientos complejos.
- **Active Record:** combina persistencia y lógica de negocio, generando mayor acoplamiento.

## Consecuencias

**Ventajas:**
- Centralización de reglas de negocio.
- Mayor consistencia.
- Facilidad de mantenimiento y pruebas.
- Separación de responsabilidades.

**Desventajas:**
- Mayor complejidad inicial del diseño.
- Necesidad de definir correctamente las entidades y agregados.

## Evidencia de implementación

`src/edutech/domain/model.py`

Contiene entidades y comportamientos relacionados con cursos, inscripciones, cupos, calificaciones y certificaciones.
